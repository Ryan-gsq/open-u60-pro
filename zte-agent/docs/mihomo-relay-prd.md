# Mihomo 与 Wi-Fi 中继：产品需求（PRD）

更新：2026-11-12（批次 4）。本文是现行行为的总览，按本仓库 v1–v6 重构后的源码写（[实现与验收记录](relay-mihomo-implementation.md)），
其中标“待设备验收”的部分还没有在 B31 上验证。细节、实现依据和实测记录以下列文档为准：
[network-extensions.md](network-extensions.md)（功能、安全、API、恢复）、
[relay-hw-offload.md](relay-hw-offload.md)（IPA 硬件转发、Mihomo 的 DIRECT 绕过）、
[relay-lifecycle.md](relay-lifecycle.md)（中继连接、断开和恢复流程）、
[web-ui.md](web-ui.md)（页面）。这里的数字都来自那些文档的实测记录，本文没有单独验收。

## 1. 目标

- 热点和 USB 下的设备可以经 **Wi-Fi 中继**连到酒店或家里的 Wi-Fi 上网，不消耗蜂窝流量。
- 可以按订阅规则走 **Mihomo 代理**；在约 240 Mbit/s 的线路上尽量少占 CPU。
- 只在 agent 的网页和 API 里提供；iOS/Android App 不变。

## 2. 数据路径

| 流量 | 路径 | 由谁转发 |
| --- | --- | --- |
| Mihomo 关，IPv4 | 客户端 → 内核 NAT → 中继 | 极速模式下 IPA 硬件（TCP 和 UDP/QUIC 都会被卸载），其他工作模式 CPU（第 5 节） |
| Mihomo 关，IPv6 | NAT66 → 中继 | CPU |
| Mihomo 开，规则判为 DIRECT 的 IPv4（打开绕过开关时） | 在内核里绕过 Mihomo，走内核 NAT | 同 Mihomo 关时的 IPv4 |
| Mihomo 开，其余 IPv4、全部 IPv6 | TPROXY 进 Mihomo → 节点或直连 | CPU（Mihomo 进程） |
| 路由器自己的流量 | 不经过 Mihomo，直接出去 | CPU |

中继和蜂窝互不影响：中继连着时优先走中继；断开中继只撤掉自己的路由，**不会主动打开蜂窝拨号**、
不改 APN。蜂窝没开或不可用时，断开中继后就没有外网。

## 3. Mihomo

### 3.1 管理

- 安装固定版本：mihomo 1.19.33、Zashboard 3.29.1，下载后校验 SHA-256，不自动升级。
- 最多存 16 个配置。来源：HTTPS 订阅（手动或定时刷新）、文件导入、粘贴。
- 选中的订阅刷新时，相同源只更新刷新元数据；内容改变由控制器校验候选一次后热重载，不停核心。
  热重载不支持的启动设置改变、核心拒绝或变更订阅的结果未知时，用已校验候选做保留拦截的重启，
  启动失败回退最后应用的配置。切换配置、修改生效配置内容和修改扩展仍按配置变更重启。
  成功刷新已在路由器验证，失败回退尚未验证，证据与边界见[批次 4](relay-mihomo-implementation.md#batch-4)。
- 全局 Merge 和 JS Script 扩展在服务器端执行，有内存、时间上限；失败时保留旧配置。
- 代理页可以切模式（rule/global/direct）、选节点、测延迟；Zashboard 经同源桥接打开，浏览器拿不到核心密钥。
- 开关打开成功后记下选择，agent 或路由器重启后自动恢复；关掉即清除。

### 3.2 拦截

- 只拦截从 `br-lan` 进来的 TCP/UDP，IPv4 和 IPv6 都拦，用 nft TPROXY 转到 17894 端口
  （表 `ip`/`ip6 u60_mihomo`）。运行时 `bridge-nf-call-ip(6)tables=0`、TCP pacing 比例为 1000，停止时恢复。
- LAN 的 DNS（53）重定向到 1053。DNS 固定为 fake-ip（owner decision 64）：IPv4 地址池 `198.18.0.1/16`，
  不配 IPv6 地址池。rule 模式的 `fake-ip-filter` 只取决于配置和绕过开关：只有规则里直接写 `DIRECT`
  的固定域名给真实地址；策略组后面的域名（即使当前选的是 DIRECT）和会刷新的规则集一律给假地址，
  所以切组不改 DNS，客户端也拿不到会被切走的域名的真实地址（车主选择 Q2、Q3）。
- 本地、私网、Tailnet 地址不进 Mihomo。

### 3.3 在内核绕过 DIRECT 流量

页面上叫 "Bypass Mihomo for DIRECT rules"，接口 `POST /api/mihomo/cn-direct`，**默认关**。

| 模式 | 在内核绕过的 IPv4 |
| --- | --- |
| rule | 按规则顺序编成内核链：按地址判 DIRECT 的规则放行，其他目标交给 Mihomo；内核判断不了的非 DIRECT 规则处截断 |
| direct | 全部（fake-ip 地址除外） |
| global，或开关关着 | 不绕过 |

- 策略组只有沿 `select` 的当前选择最后落到 DIRECT 才算 DIRECT；`url-test` 等自动组不算。
- 在控制台或 Zashboard 改模式、改组选择、改规则集时，由控制器排序：先收紧内核绕过，再写核心、读回，
  只重置失去 DIRECT 的连接（能按目的地址算出时只重置那些地址段，否则重置整个 LAN IPv4），最后装新链；
  不重启 Mihomo。核心每 60 秒读回一次，发现差异按同样顺序跟上。
- `http` 规则集由 agent 按订阅间隔刷新（核心不再自己刷新）；刷新期间按“未知”处理，不让它绕过核心。
  `domain` 规则集不进内核链，刷新时直接交给核心，不收紧、不换表。
- 同一配置下，绕过开关会改变 DNS 过滤表；选中订阅刷新也可改变配置及过滤表。先保持拦截，再热重载
  （`PUT /configs`），核对模式、出口、选择、规则集和监听；过滤表改变时还核对 1053 的回答。
  核对不了就用已校验候选做保留拦截的重启，不再重复校验。核心全新持久缓存的第一次重载可能清空 fake-ip 池，
  后续保留映射；该核心限制只在本机真实核心复现，未在路由器验证，未作规避（批次 4）。
- IPv6 始终全部进 Mihomo。

### 3.4 看护

- ZTE 改写防火墙、sysctl 或路由后，由 `net_guard` 补回：事件安静 2 秒后立即核对，补回过东西 5 秒后再查一次，
  没有事件时每 60 秒兜底；事件后的 3 秒内每 0.5 秒检查一次 Mihomo 持有的 brnf 等 sysctl。
- 中继出口的 IPv4 变化立即重启 Mihomo；只有 IPv6 变化时要持续 5 秒、两次间隔至少 60 秒。
- 计划内重启（换配置、换出口）先在旧核心还在服务时准备并校验新配置，再保持拦截、停旧核心、起新核心：
  这段时间核心起不来时流量被挡住，不会直连。新配置校验不过时旧核心继续服务；校验过了却起不来时退回上一份。
  只换出口接口时复用之前的校验（同一次开机记住最近 4 份）。
- 核心意外退出、或计划内重启最终失败时，撤掉常规拦截、页面显示“正在直连”，只保留 fake-ip 地址的快速失败；
  然后按 5/15/30/60 秒、之后每 5 分钟重试（D2、D3）；开机恢复或中继带来新的 IPv4 出口时立即重试。
  撤拦截本身失败时页面不说“正在直连”，按同样的间隔再撤。**不是防泄漏的 kill switch。**
- agent 自己退出时（Mihomo 控制器线程 panic 也会让 agent 退出），独立的守护进程重跑启动脚本拉起它，新 agent 接管同一次开机里的拦截，不经直连窗口；
  连续 3 次起不来才恢复直连并每 5 分钟再试（Q1）。OTA 试运行期间交给更新助手。

## 4. Wi-Fi 中继

### 4.1 支持范围

- 上游：2.4 GHz 或 5 GHz（包括 DFS 信道）；开放网络和 WPA2-Personal。
- 不支持：隐藏网络、企业认证、只有 WPA3 的网络、只有 IPv6 的上游、NAT64/464XLAT。
- 前提：5 GHz 主热点开着，访客 Wi-Fi 关着；2.4 GHz 上游还需要 2.4 GHz 热点开着。

### 4.2 连接

- 2.4 GHz 上游：热点重新配置到上游的信道（20 MHz）。
- 5 GHz 上游：热点先切到一个非 DFS 的 20 MHz 信道过渡，关联上游后让热点跟到上游信道；关联前打开驱动的
  DFS 切信道开关（owner decision 62：持久设置厂商键 `wireless.zte_mbb.dfs_channel_switch_disable=1`，
  再 `iwpriv wlan2 disableDfsCS 0`）。过渡信道这一步没有配置能代替（报告 B）。
- 连上后：DHCP、IPv4 策略路由（表 60631）、NAT、DNS 转发，临时关掉 ZTE 的离线门户；5 GHz 网络之间切换时
  这个抑制原样交给新连接，不会中断。
- 可选的 IPv6（默认开）：NAT66，加上 LAN 上本地 ULA 地址的 RA。
- 防火墙（待设备验收）：拒绝规则都在 agent 自己的 nft 表 `ip`/`ip6 u60_relay`，排在 ZTE 规则之前：
  站点接口 `ath20` 拉起前就挡住上游进来的连接（只放已建立连接和 DHCP），断开后才撤；没装路由时不转发任何
  经上游的流量；IPv6 到蜂窝一律拒绝；NAT66 的地址转换也在 nft。legacy iptables 只留必须穿过 ZTE 拒绝
  规则的放行、门户 RETURN（保证排在厂商 DNAT 之前）和 IPv4 MASQUERADE。
- 状态只显示"已配置 / 外网未验证"，不代表酒店已认证或外网可用。

### 4.3 运行和断开

- 每 3 秒检查关联、DHCP 和辅助进程。**上游掉线就清理中继，运行中不自动重连**，也没有外网探测。
- 断开时恢复原来的热点；5 GHz 可能要等约 60 秒雷达检测（CAC）。
- 中继或 Mihomo 占用网络时，agent 自己的 Wi-Fi、访客、LAN、USB、厂商防火墙修改会拒绝冲突的写入；
  正在进行的中继操作最多等 3 秒，厂商异步 Wi-Fi 重载跟到热点真正恢复才算结束（v4）。

### 4.4 重启恢复

- 只恢复最近一次成功的连接（`/data/zte-agent-relay/resume.json`，记住了密码或是开放网络时才写）；不轮询所有已保存的网络。
- agent 重启后，上一个 agent 留下的中继连接仍有效时直接接管，不断开重连，Mihomo 只启动一次；接管不成立和整机重启时，先恢复 Mihomo，再重连中继，中继最多重试约 17 分钟；手动连接、断开或关热点都会取消重试。
- 手动断开会清除这个选择；上游掉线不会清除。

### 4.5 每个网络单独保存的选项

- 是否记住网络（默认记住）；Forget 删除记住的密码，不断开当前连接。
- 带宽：始终保持协商带宽。自动调优在 v6 删除，关联后的宽度复位在 2026-11-12 删除；
  以前保存的“自动调优”按保持协商带宽处理。

### 4.6 上游省电（owner decision 65）

默认每次连接都关掉站点 `ath20` 的 802.11 省电（实测短测速从 166–218 提到 244–250 Mbit/s）。
开关在中继页，改动对当前连接立即生效。和路由器的省电模式无关。

## 5. IPA 硬件转发（owner decision 63、64）

- **不用安装**：B31 原厂的 `IPACM_cfg.xml` 已经列着中继的站点接口 `ath20`，agent 只读这个文件、从不改它，
  也不需要重启路由器。页面一行 “IPA CONFIGURATION” 显示文件是否列着它（2026-11-12 之前要装一个 `u60sta0` 条目
  并重启，这一步已删除）。
- **运行时开关**：关掉后当前连接立刻改走 CPU，打开立刻恢复硬件转发，不用重启也不用重连中继。
  每次切换会重置一次 LAN 的 IPv4 连接。
- **连上时自动做的事**：加一条 main 表默认路由（metric 60631），让 IPACM 把中继当作 WAN。
- **HW/SW 模式归路由器**（车主决定，2026-11-12）：agent 不读、不切、不核验 IPACM 的模式。工作模式为
  极速模式（Balanced，`Nomal_mode`）时加速打开；其他工作模式、限速、省电模式或 `ipa_disable` 会关掉它，
  智能模式（`Ai_mode`，出厂默认）和游戏模式还会随流量来回切。要用硬件转发，车主自己选极速模式。
  页面在路由就位时写“极速模式下走硬件，其他工作模式走 CPU”，不确认卸载是否真的发生。
- **绕过 IPACM 的两个问题**（`relay-hw-offload.md` 第 8、9 节）：
  - 上游其他设备抢走硬件上行：把那台设备的 MAC 移出 IPACM 的上行规则。
  - 热点客户端换频段后丢了 LAN 路由：客户端关联 5 秒后，把它的 ARP 条目设成 STALE 一次，不断开它。
- 永远不重启 ipacm，不踢客户端。

## 6. 开关和默认值

| 设置 | 默认 | 接口 |
| --- | --- | --- |
| Mihomo 开关 | 关；打开后重启路由器仍会自动恢复 | `POST /api/mihomo/switch` |
| Mihomo 模式 | 跟随配置 | `POST /api/mihomo/mode` |
| DIRECT 绕过 | 关 | `POST /api/mihomo/cn-direct` |
| DNS | fake-ip（固定，不能改） | — |
| 连接表单：记住网络 / IPv6 / 确认提示 | 都勾选 | `POST /api/wifi-relay/connect` |
| 带宽 | 保持协商带宽（不可调） | — |
| 自动关上游省电 | 开 | `POST /api/wifi-relay/power-save` |
| 硬件转发开关 | 开 | `POST /api/wifi-relay/offload`（`{"enabled":bool}`） |

## 7. 明确不做

- 不做 kill switch；不代理路由器自己的流量；不支持 PROCESS-NAME 规则（热点客户端的进程认不出来）。
- 中继运行中不自动重连、不后台扫描、不做外网探测。
- 不重启 ipacm，不踢客户端，不替换系统自带的 `wpa_supplicant`；UCI 持久配置只改 DFS 切信道开关的厂商键
  （车主 2026-11-12 批准），不改 IPACM 的配置文件和 HW/SW 模式。
- 不改 iOS/Android App。

## 8. 已知代价和限制

- 被硬件卸载的连接不经过 iptables、tc 限速和家长控制；走 CPU 的中继流量也在 ZTE 的家长控制、网址过滤之前
  被放行，所以这两项对经中继的设备都不生效，页面上有提示（D8）。
- Q2/Q3 的代价：订阅里大部分域名在策略组后面，现在都给假地址、进核心，能被硬件卸载的流量比以前少；
  吞吐和 CPU 待设备对照。
- Mihomo 运行时 brnf 为 0，访客隔离这类 LAN 内部的过滤会失效（用户已接受）。
- IPv6 只能走 CPU：NAT66 时 CPU 30–56%，按推算单流大约在 300 Mbit/s 见顶（没有实测）。
- 被内核绕过的连接不会出现在 Mihomo 的连接列表和流量统计里；用 DoH 或写死 IP 的客户端只能按地址分流。
- agent 重启那几秒里 IPACM 给上游设备建的规则会残留，只有重启路由器能清掉。
- 5 GHz 中继断开、或从 5 GHz 切到 2.4 GHz 上游，要多等一次 CAC；5 GHz 网络之间切换不用等（热点只回非 DFS 过渡信道）。

## 9. 实测数据和待验收项

约 240 Mbit/s 的上游（W_Game 52/160，Mac 连 G）：

| 路径 | 速率 | CPU |
| --- | --- | --- |
| 硬件转发，IPv4 | 238–240 Mbit/s | 8–12% |
| Mihomo（TPROXY），单流 | 190–238 Mbit/s | Mihomo 31–44% |
| 测速：经中继 / 直连上游 | 244–253 / 291–295 Mbit/s | — |

还没验证（v1–v6 各版本的维护窗口清单见[实现与验收记录](relay-mihomo-implementation.md)）：

- 蜂窝在线时和中继共存的行为，以及 IPACM 在两个 WAN 同时存在时的选择；
- 2.4G 上游加硬件转发；
- 长时间运行的稳定性；
- 酒店门户认证；
- RPS 和硬件转发同时开的效果；
- 客户端换频段后卡住的场景，修复后还没有自然复现过。
