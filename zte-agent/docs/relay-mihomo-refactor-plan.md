# Wi-Fi 中继与 Mihomo：版本与验收

定稿：2026-11-10。行为以[架构规范](relay-mihomo-architecture.md)为准；本文件规定按什么顺序交付、每版怎样证明可用和可回退。v1–v6 指本次重构的交付批次，不是已发布的 OTA 标签。工作区已有部分 v1 改动；下面的门槛不等于已验收或已部署。

## 1. 验收基线

2026-11-10 留存的 B31 记录：OpenWrt 23.05.4、内核 5.15.194、nft 1.0.8、iptables-legacy、conntrack-tools 1.4.8、Mihomo 1.19.33。网络为 W_Game 5 GHz、IPv6 NAT66、IPA HW、rule 模式、IPv4 DIRECT 绕过打开。ARM64 release 基线为 section Total **8,915,528 B**、`gzip -n -9` **4,385,216 B**。以下是对照数据，不是新版的测试结果。

| # | 已知事实与可以用来检验的结论 |
| --- | --- |
| 1 | B31 两次 fw3 **reload** 中，上游 INPUT 钩子未丢；当时 ZTE 对未入 zone 的 NEW 连接最终 reject（规则推断）。整表 restart/flush、第二台上游设备实连、IPv6 RA/NS 恢复须另测。 |
| 2 | 一次 reload 耗时约 2.8 s，brnf 约 3.6 s 处于错误值，门户 RETURN 缺约 5 s。60 s 兜底不是正常恢复目标。 |
| 3 | 曾杀核心，≤1.8 s 撤拦截，≤2.5 s 恢复 brnf/撤策略规则；20 s 内未自动恢复。手动启动约 4.96 s，拦截约 5.3 s 就位，`mihomo -t` 约 1.7–1.8 s。未抓到“这 1.8 s 每个包都直连”的证据。 |
| 4 | 真实 IPv4 硬件下载中按目的 /24 删除 conntrack，路径未变，下载未断；IPACM 处理 DESTROY 后约 90 ms 重新卸载。**尚未证明失去 DIRECT 的旧硬件流会退出**，v2 要做正向用例。 |
| 5–6 | ZTE 会把自己的链插在 FORWARD 最前。家长控制、网址过滤位于中继放行之后；原 NAT66 放行与基线拒绝的钩子若颠倒，合法 IPv6 会被拒。不能只验规则数量或存在性。 |
| 7 | 当时双栈客户端的外网连接中 IPv6 约占 37%，DIRECT 的真实 AAAA 也会进核心。D4、M14：保留 IPv6，不引入 IPv4 优先；按各自数据路径比较性能。 |
| 8 | 该订阅的核心 DNS 使用 DoT/DoH，未触发端口 53 改写；明文 DNS 配置需另验核心标志位及原目的。 |
| 9 | IPACM 监视 `/etc/data/ipa` 目录的 MODIFY/MOVED 事件；这不能证明截断写入能抗进程死亡，也不能代替“接口表已在本次开机加载”的判断。 |
| 10–11 | agent 自身约 0.8% 单核，派生工具约 2%。核对曾占锁约 0.5–1.6 s，探测写请求约 3–4% 得到假 409。优化优先验证正确性和等待，不用派生进程数代替结果。 |
| 12 | v1.19.33 源码确认热重载会暂停接入、更新 DNS 并保留可用映射；204 不能证明 provider、实际选组或监听正常。旧 UDP、hy2、长时间内存及重载耗时须实测。 |
| 13 | 核心按 interval 更新 provider 时即便内容相同也可改 mtime。测试订阅有 11 个每日更新的 rule-provider；相同内容不能引发重编、换表或重置。 |

reload 前规则/sysctl 快照曾在设备 `/data/zte-agent-backup/fw-reload-test/`；它和 IPACM、zwrt_router 的旧备份已于 2026-11-11 按车主要求删除（[项目约定](../../CLAUDE.md)）。更多原理与实测见[硬件转发](relay-hw-offload.md)、[网络扩展](network-extensions.md)和[TPROXY 单流测量](../../docs/research/2026-11-08-mihomo-tproxy-single-flow.md)。

## 2. 发布顺序

| 版本 | 阶段 | 可单独验收的交付物 | 发布前必须证明 |
| --- | --- | --- | --- |
| [v1](#v1) | 0、1 | 小修、工具、可观测性；沿用现行日志格式 | 基线不变；conntrack 错误不能报成功；不会误杀人工监视器 |
| [v2](#v2) | 2、3 | 效果层、Mihomo 控制器、保留拦截重启和精确重置 | 新旧日志能实际回退、首次占用不抢外部资源、旧退出事件无效、失败的目标表会重试；agent 意外退出后无需人工恢复 |
| [v3](#v3) | 4 | 同一配置的 DNS 过滤表热重载 | 204 之外核对运行状态与真实 DNS/出口；失败/超时可恢复 |
| [v4](#v4) | 5、6 | 中继控制器、准入、IPA 状态机 | 中继 CAC 不能阻塞 Mihomo 的退出处理或 brnf 核对；开关/限制/崩溃的资源能正确释放 |
| [v5](#v5) | 7 | nft/legacy 防火墙布局、ZTE 恢复和 DNS 标志位 | 合法双向转发、上游全周期防护、NAT66 与 IPA 都有数据面验证 |
| [v6](#v6) | 8 | 删除带宽调优、完成模块和界面整理 | 已保存网络可迁移，关联复位仍在，文档与已发布行为一致 |

以下保留实施条目编号（N 网络、M 核心、R 中继、H IPA、S 结构、U 界面/文档），方便现有代码和测试引用。各版本都执行 §3 的共同门槛。

<a id="v1"></a>

### v1 · 基线与小修（阶段 0、1）

**交付。** 搬入有界命令/私有文件工具和网络编号（S2、N10），保留不同用途的豁免地址子集；`uci get` 限时 3 s（N9），日志带 CLOCK_BOOTTIME（U2）。统一 conntrack 调用、直接传参，区分零匹配、删除失败和实际删除（N8）；UI 提示按实际结果（U1）。按现有核对机制覆盖 wireless 事务的上游防护（N1），管理端拒绝上游 STA 对端（D1、N3）。交互写操作最多等 3 s，自动看护不等（D9、N6）。只有实际出口变化才通知；核心关闭或安装中不因该通知报错；空会话断开不重启核心（M2、M10、R4）。规则文件以内容哈希判变化（M8）；只清本 agent 对应的孤儿（R2）。记录 IPACM 写入的持久性风险（H5），修复和故障验收在 v4。

**验收。** 测 conntrack 匹配、零匹配、退出码相同但诊断为操作失败；只改 mtime 不重编；无会话断开、扫描失败不触发重启；人工同名 `iw event`、复用的 PID 不被误杀。设备做真实 reload 和两分钟无副作用准入探测，分开统计“正在操作”的假 409 和资源确实冲突的 409。v1 不写后续版本才认识的撤销记录。

<a id="v2"></a>

### v2 · 效果层与 Mihomo 控制器（阶段 2、3）

实现 `EffectSet` 及内部效果注册（S1、S2）；串行 Mihomo 控制器、退避、启动和保留拦截的重启（M1、M3、U3）；纯规则规划、两族整表替换、差集与实际重置（M4–M6、D10）；出口去抖（M9、D7）、桥接写排序及 503（M11）、保留 `no-resolve`（M12）。在 v4 迁移中继前，既有中继仍通过同一入口发布出口观测。此版 DNS 过滤变化可走受保护的重启，不以热重载尚未交付为由撤拦截。

> 2026-11-12 注：`EffectSet` 没有实现，车主决定暂不做；效果层实际是 `net_tools::Transaction` 加 `netfx::effect::NftTables`（[架构规范](relay-mihomo-architecture.md)“规定了但未实现”）。

**四项发布阻断：**

1. **日志兼容。** 用实际旧版读取并执行新版生成的 undo；覆盖同一 boot 下 OTA 试运行切回旧槽/可启动的旧 Stable。解析成功但跳过新效果仍不合格。另测跨 boot 不重放旧热点/RA；独立 CLI 清理与正常启动走同一恢复逻辑。
2. **资源归属。** 预放同名外部表、链、优先级和相同文本的规则；首次声明应拒绝。分别在写完 undo 未执行、首项后、两族/不同表之间、撤销途中杀进程。只撤自己的，保留外部规则、外部 RA 改动和未完成日志；重试能收敛。
3. **进程代次。** 旧 `CoreExited` 晚于新核心就绪、旧重试晚于车主关闭、后台校验晚于换配置，都不能改变新意图、清掉新拦截或重新拉起旧核心。只允许一个回收者；清理失败对外显示待恢复。
4. **失败目标不丢。** A→B 首次 `nft -f` 故障且 A 完好，核对必须继续尝试 B。覆盖内核已提交但读回失败、集合超过 256 KiB、子命令超时；保留保守计划，不把旧哈希或只见到链名当作 B 已生效。

**数据面验收。** 在受控 Linux QA 核对 `NFT_BREAK`、已有透明 TCP、新 SYN 到普通远端 17894、表替换及双栈标记交付；B31 空闲时复测。让一个可识别的**真实 IPv4 硬件长流**经独立 `IP-CIDR` 规则从 DIRECT 切走，须在记录的时间内停止旧出口或改经核心；另一条未变 DIRECT 下载须继续。用前置 `DST-PORT,443,PROXY`、来源条件、组合规则、>64 段及两次变化相隔 <200 ms 的反例验证兜底。反方向切到 DIRECT，原在核心中的 TCP 应继续传输；另测 UDP。用 §3 双出口探针，在 provider 自主收紧规则或更改组成员时，刻意延迟通知或兜底核对；整个窗口都不得出现直连出口。

**故障验收。** 守护 agent 存活时，意外杀核心后按 D3 临时直连、fake-ip 快速失败，随后按 D2 退避恢复；在正常测试配置上验证首轮约 10 s 的目标，分别记录检测、5 s 退避和客户端恢复时间。启动错误、3 次短期退出、车主取消、撤销失败都需覆盖。分别在 Running 和计划切换中模拟 agent 退出；不手动启动 agent 或改规则，验证同 boot 自动拉起且只有一个 owner，DNS 和实际客户端出口按持久意图恢复。再测 OTA 健康试运行失败回旧槽，恢复机制不能抢回候选版。记录退出至可用的时间；单杀核心不能替代这项验收。

<a id="v3"></a>

### v3 · 热重载（阶段 4）

**交付（M7）。** 仅对同一配置的 `fake-ip-filter` 变化调用 `PUT /configs?force=false`。沿用 v2 的先收紧、核验后再扩大；保留运行时 mode、log-level、出口接口、凭据和已确认的旧配置。实际状态不符或 PUT 结果无法确认时，保留拦截，走经校验的重启。热重载用于切换整份订阅不属于本版通过条件。

> 2026-11-12 批次 4 补记：以上保留 v3 的原交付范围。当前选中订阅的手动/定时刷新也使用热重载，相同源跳过编译/校验；改变的源由控制器校验候选一次，失败重启直接复用该候选，起不来回退最后应用配置。启动设置变化仍重启，切换配置、修改生效配置内容和修改扩展仍按配置变更重启。全新持久缓存第一次重载可能丢 fake-ip 映射，只在本机真实核心复现；成功刷新已在路由器验证，失败回退未在路由器验证。证据与边界见[批次 4](relay-mihomo-implementation.md#batch-4)，不能将本条补记当成下面完整发布门槛都已通过。

**发布门槛。** 核对 `/configs`、`/proxies`、所需 provider/监听及 1053 的真实/假地址答案；测试 204 但 provider 为空、意外退到 `COMPATIBLE`、客户端超时而核心已 apply、保留旧选择和运行时接口。用 §3 双出口探针、已有 TCP 与 UDP/QUIC/hy2 分别观测；运行 10 次重载记录暂停时长、实际丢包和内存趋势。新查 DNS 与复用切换前缓存的真实 A 必须是**两个**测试：先通过路由器 DNS 获得真实 A，再把其域名从 DIRECT 切为代理，同时保留覆盖 A 的 DIRECT 地址前缀；客户端不再查 DNS，用旧 A 新建连接。代理可用时目的端应观测到代理出口，切换或不能判定时可暂时阻断，绝不能观测到直连出口。

<a id="v4"></a>

### v4 · 中继控制器与 IPA（阶段 5、6）

**交付。** 中继会话、取消和开机恢复串行；3 s 观测与决策分开，DNS/resolv 只由 uplink 声明（R1、R3、R6、N7）。实际装过/撤过路由才发布新出口，单纯换 DHCP DNS 也更新下载器；核心不运行时同样可用。实施按操作区分的 Admission 与异步 reload 的占用期，取消不被占满的 Slow lane 拦在门外。`IpacmPort`、显式状态、有效吞吐核验、固件指纹和 UI 归属在此版完成（H1–H5）。

> 2026-11-12 注：中继控制器线程没有实现（车主决定暂不做），仍由 tick 与调用线程经 `op` 串行。批次 4 已完成阶段快照、车主请求对准入和 `op` 合计最多 3 s 的等待及操作中接受断开；锁序现在是 `op` → `inner` → `restore` → `snapshot`，状态只读内存。Connect 前置选择校验等 `inner` 的时间也计入这 3 s。IPA 的 HW 模式切换、车主限制和“有效吞吐核验”（回程计数、重新挂载）已删除，模式交给路由器的工作模式（[硬件转发](relay-hw-offload.md)）。下面 IPA 矩阵中的“车主限制”“原模式”“回程计数”“Software/Engaging”各项随之不再适用。IPACM 配置的安装也已删除：站点改名 `ath20`，原厂配置已列着它，所以“首次安装需重启”“同 boot 再装”“移除”和配置写入的各项同样不再适用。

**发布阻断：** 在 wireless 撤销阻塞最长 CAC 的同时，触发另一个 owner 的 sysctl 修复和核心退出。guard 须跳过忙 set 并核对 Mihomo；退出检测目标 2 s 内，之后遵守自己的退避。不能只证明两个控制器线程都活着。模拟迟到的核对，不得在释放 brnf 之后又写回运行值。

**验收。** 测有效会话上的扫描、换网前校验失败、错密码且从未装路由、装路由后才失败、重复断开、关联 12 s 内恢复与超时、清理失败。发起厂商异步 Wi-Fi reload 后马上连接，两个 Slow 请求期间手动取消，验证资源互斥、意图和结果。核心关闭时变更租约 DNS、随后断联，下载器不得继续用旧地址。

**IPA 矩阵。** 分别验证首次安装需重启、同 boot 曾加载后再装、打开/关闭/移除、车主限制出现与解除、指纹不符及 main 路由失败。检查 main 路由、原模式、监视器、实际 conntrack 结果、受控 TCP 负载下的回程计数。Software 下的关闭/移除有出口，解除限制能重入 Engaging，空闲不能宣称已经卸载。配置写入中断的实验先在副本/故障注入环境做；到设备验证属主、权限、SELinux 标签、备份及下次加载。绝不运行时重启 ipacm。

<a id="v5"></a>

### v5 · 防火墙、NAT 和改写恢复（阶段 7）

**交付（N2、N4、N5、M13，D6、D11）。** 按架构 §4.3 输出**完整有序**的两族规则。INPUT 从接口起来前到断联后；FORWARD 去程、回程例外在本方兜底 drop 前，v6 的 `rmnet*` 拒绝在本地例外前。只保留一条由中继基线拥有的 v6 OUTPUT 拒绝。门户 RETURN 保证在厂商 DNAT 前；只对确需穿过厂商拒绝的包在 legacy 放行。NAT66 迁到 nft；IPv4 MASQUERADE 只有在 NAT 和 IPA 双双通过时才迁移。核实空闲 mark 位后才部署核心明文 DNS 的 OUTPUT 豁免。

**验收。** 在真实内核先验 `nft -c`、两族 nft 批处理、`iptables-restore --noflush --wait` 对**自有**链的效果。设备依次测：纯扫描、关联、首租/续租/重绑定、断开；从第二台上游设备访问 v4/v6 9090/9443 及其他受保护监听；RA/NS/NA 和错误 ICMPv6；IPv4/v6 双向数据；IPv6 关闭、租约过期和重装期间的蜂窝出口防护；保留合法的 LAN/本地/组播路径。对明文 TCP/UDP DNS 检查核心原目的与中继普通 DNS，确保标志不破坏 TPROXY。

连续两次 fw3 reload、再在维护窗口分别测 restart/flush、只丢单钩子、厂商在前面插终局规则、脚本与自身事件重叠。记 brnf 和门户 RETURN 实际恢复时间、5 s 复查结果；restore 命令成功不算数据面通过。IPv4 NAT 测路径未变的硬件下载：同基线链路下 ≥220 Mbit/s，回程 CPU 计数仍在几百包量级；失败则保留 legacy IPv4 MASQUERADE。NAT66 另测实际双向连接。

<a id="v6"></a>

### v6 · 无线调优退役与发布文档（阶段 8）

**交付（S3–S5、R5、U4；D5、D8）。** 完成剩余模块拆分；删除 `width` 自动调优、对应采样器、`/api/wifi-relay/tuning` 和页面选项。保留关联时的宽度复位，以及热点需要的解析/窄化函数；已存 `auto` 读作 `off`。同步实际部署行为到[产品说明](mihomo-relay-prd.md)、[网络扩展](network-extensions.md)、[硬件转发](relay-hw-offload.md)、[中继生命周期](relay-lifecycle.md)、[Web UI](web-ui.md)及仓库约定。提示 ZTE 家长控制/网址过滤、IPv6 CPU 路径和硬件状态的真实适用范围。

**验收。** 使用含旧选项的已保存网络连接，验证凭据/恢复选择仍有效、一次性宽度复位仍执行；W_Game 5 GHz 和另约时段的 W 2.4 GHz 都测一次，验证热点恢复和硬件路径。检查页面/API 与旧设置迁移、release 大小；不能把删除行数当作性能或体积达标。

> 2026-11-12 注：关联时的宽度复位也已删除，agent 不再运行 `iwpriv … chwidth`（报告 B：调优器删除后唯一的写入者就是复位本身）。

## 3. 共同门槛及维护窗口

- **写入边界**：随各版本迁移把相应路径纳入源码扫描测试；绕过 `netfx` 直接写上述网络资源时，全套 host 测试应失败。放行例外以架构 §4、§4.7 为准。
- **每阶段**：开发机 `cargo test --locked -p zte-agent -- --test-threads=4`；发布构建 `cargo build --locked --release --target aarch64-unknown-linux-musl -p zte-agent`。记录同一产物的 `aarch64-linux-musl-size -A` Total（本 Mac 可用 `xcrun llvm-size -A`）和 `gzip -n -9` 字节数。涉及网络状态的版本先跑假端口/时钟和一次性 Linux QA，再按[部署规范](../../CLAUDE.md)在约定的空闲窗口部署验收。没有设备结果就标未验，不根据单测或代码存在标记“已发布”。
- **代理出口实证**：用两个可控、可区分直连与代理源地址的目的端，从 LAN 每 100–200 ms 新建请求；一个真实 IP 按规则必须代理，一个明确 DIRECT 作对照。分别测计划内重启、切组、热重载、agent/桥接入口。允许暂时失败的切换阶段，代理探针只能看到代理出口或失败，不能看到酒店/蜂窝出口。另测域名、旧真实 A、新查 fake-ip、已有 TCP、UDP 和失去 DIRECT 的 IPA 流；记录切换时间线。PID、conntrack 快照、保持一个无关下载都不能独立证明没有漏包。
- **恢复与回退**：在隔离环境注入部分提交、外部占用、权限错误、控制器响应丢失、过期消息；核对日志、状态页和内核实际状态。设备上至少一次新版活动时异常终止、启动受支持的旧二进制，模拟 OTA 自动回旧槽。确认干净撤销或按持久意图重新取得资源，两者应有可区分的观测点。不同版本是否能独立回退以此为准，不要求新版先活着关闭功能。冷启动另验 boot id、原厂启动同步和 owner 意图。
- **开销与隐私**：同网络、带宽、模式和客户端对照吞吐、回程包数及 CPU。状态/日志带单调时间、代次、失败原因和结果，不输出凭据、secret 或 cookie。临时测试和备份按项目固定目录处理。

| 版本或验收 | 对使用者的影响，应单独约时间 |
| --- | --- |
| 全部版本 | 活动会话中的部署、异常终止、同 boot 回退和整机重启均可能中断网络；完整崩溃矩阵先在 QA 做。 |
| v1、v5 | fw3 reload 曾让 TPROXY 短断约 3–4 s、门户 RETURN 缺约 5 s；restart/flush 会暂时清掉厂商防火墙，须单独安排。删钩子、注入 ZTE 改写也只在维护窗口。 |
| v2、v3 | 杀核心、故意用坏配置、切组、切出口或撤硬件流会中断相应连接；计划内重启通常数秒，热重载会短暂停接并丢 UDP 上行。不能为了验证而在日常使用中执行。 |
| v4、v6 | 连接/断开/错密码、切频和复位可影响热点；5 GHz CAC 最长约 80 s。切 IPA、移除及重装会重置 LAN IPv4，首次安装还需整机重启（2026-11-12 起没有安装和移除，只有开关）。 |
| 专项环境 | 门户 AP 认证前后重试；可控上游 IPv6 抖动/续租；蜂窝在线与中继并存；2.4 GHz 硬件转发、客户端换频后 5 s 修复；正常使用下 24–72 h 稳定性。分别记录，不由一次 B31 冒烟代替。 |

## 4. 车主已定行为与验收

2026-11-10 车主已确认 Q1–Q3 全部采用 A；D1–D11 保持生效。这三项是实现与验收要求，不表示实机验收已经完成。

| 关联版本 | 已定行为 | 通过条件 |
| --- | --- | --- |
| Q1 · v2：agent 自身死亡 | 无需人工干预，独立于 agent 的机制自动拉起它并恢复上网；自身崩溃与单独核心退出分开处理。 | 正常运行与计划切换中各异常退出一次：无手动动作、单一网络 owner、DNS 与实际出口恢复，且不干扰 OTA 自动回旧槽；若核心最终起不来，按 D3 临时直连并重试。 |
| Q2 · v2/v3：自主 provider 变化 | 应代理的流量在自主刷新期间也不误直连。无法证明始终 DIRECT 的动态范围先走核心，稳定且可证明 DIRECT 的仍可卸载。 | 延迟更新通知，在刷新前、中、后持续探测；应代理的请求不能出现直连出口。60 s 兜底不构成宽限。 |
| Q3 · v2/v3：旧真实 A | 使用路由器 DNS 的客户端，即便复用切组前缓存的真实 IP 新建连接，也要执行新策略；可以少用一部分硬件加速。 | 旧 A 仍落在有效 DIRECT 前缀时，新建连接也不得走直连出口；只验证新 fake-ip、清 conntrack、固定等待或确认“进过核心”都不能代替目的端实测。 |
